2. Check the scene first, then the agents
The office GLB comes from the approved refined-character version; the original .blend is kept and no export changes were saved to it.
The export excludes the Blender cameras, lights and 200 m studio floor; Godot adds its own front-angled orthographic camera, warm background, ambient fill and directional light. Interior furniture geometry and characters are kept.
Godot's real-time rendering won't match Cycles exactly, and Blender's procedural fabric wasn't ported; base colours and facial vertex colours are kept.
The three agent status cards are below the office. Above them: task input, Connect bridge, Run repo test, UI simulation.
"UI simulation": needs no Python service; only demonstrates idle → working → done, clearly labelled as simulated, no ledger produced.
"Run repo test": really calls the three modules' code, but the input is the repo's pre-extracted sample; it doesn't read your accounting files or run OCR.

Steps:

2. The terminal should show: Local Agent bridge ready at http://127.0.0.1:8765
3. In the running Godot window, click "Connect bridge"; it should show connected.
4. Click "Run repo test" and watch the status cards and current step.
5. Output goes to bridge/runs/<job_id>/: records.json, ledger.json, exceptions.json, secretary.json, result.json.

Restarting the server clears the in-memory job index but not existing result files; those may contain business data, so keep them safe.

4. How it is actually wired
Godot → HTTPRequest → local Python bridge → the reviewed agent modules.
bridge/worker.py uses separate module aliases so Logistics and Secretary (both named src) don't collide on import.
Order: Secretary Planner builds the plan → Logistics validates pre-extracted records → Financial reconciliation engine → Secretary maps exceptions and generates tasks / drafts / report.
The initial plan is the repo planner's original output; the actual execution order is controlled by the bridge. A plan that mentions OCR doesn't mean OCR ran in this round.
The original Secretary run() doesn't actually dispatch the other two, and the original dispatch_to_financial() returns a sample. The bridge skips those mock dispatches and calls the real modules with real outputs.
The original Logistics CLI only reads text and doesn't call a field-extraction model. The bridge requires already-structured fields; an image/PDF extraction module is the next stage.

5. Script interface (callable from other Godot scripts)
Assuming the calling script is on the OfficeDemo root node:
$AgentState.set_agent_status("Secretary", "working", "Generating plan")
$AgentState.set_agent_status("Logistics", "done", "Documents validated")
$AgentState.set_agent_status("Financial", "error", "Missing input fields")
$AgentState.set_current_step("Step 2: reconcile invoices and receipts")
$AgentState.reset_agents()
var snapshot = $AgentState.get_agent_state("Secretary")

Valid statuses: idle, working, done, error. An invalid agent or status returns false and leaves the UI unchanged.
Real state snapshot: $AgentState.apply_snapshot({"agents": {...}, "current_step": "..."}); all three agents must have status/step.
Submit the repo sample: $AgentClient.start_fixture("Close out September")
Submit your own extracted records: $AgentClient.start_records("Close out September", "2026-09", records_array)
Connection check: $AgentClient.connect_bridge()
Signals: AgentState.agent_changed, current_step_changed; AgentClient.job_finished(result), job_failed(message).
Don't write state from an external script while the bridge is polling; polling overwrites the UI with the server's latest state.
If the network drops, the accepted job ID is kept; click Connect bridge to resume polling. If a submit response is lost the job may still be running; the service allows one active job at a time to avoid duplicates, so check bridge/runs.

6. Local HTTP contract
GET /health: service status and capability limits.
POST /jobs: asynchronous submit, returns 202 and a job_id.
Example request: {"mode":"fixture","goal":"Close out September"}
Other request: {"mode":"records","goal":"Check pre-extracted records","period":"2026-09","records":[...records in the Logistics schema...]}
GET /jobs/<job_id>: status, agents, current_step, events, warnings and counts.
GET /jobs/<job_id>/result: original results plus the mapping once finished; 409 if not finished.
The bridge defaults to 8765; if you change server --port, also change bridge_url in the AgentClient Inspector.
The UI only offers the fixture test by default. The records input is implemented and tested, but has no upload / file picker UI.
At most 100 records and 1 MB per request; source_ref must be unique; amounts and field confidence must be real values, missing ones are never filled with 0.
Financial works in MYR only: no currency conversion, and MYR is never treated as RMB.

7. Current limitations you must know
1. This verifies the code path; it is not a production closing system. No OCR, LLM extraction, database or account integration.
2. Financial's TODAY is 2026-10-10 and period is a label only; it doesn't filter by month. Callers must filter records first; other months can't be treated as a formal close.
3. Financial and Secretary define cash flow differently: Secretary treats receipts as income and POs/invoices as spending; Financial de-duplicates payment evidence and uses other rules. The bridge keeps both outputs separately, doesn't merge the numbers, and doesn't claim a correct cash flow.
4. Financial exceptions use type/document_number, Secretary uses event_type/invoice_number. The bridge unpacks and maps them, filling actual amount, date and currency from the source_ref record; duplicate matches become document numbers.
5. Exceptions that can't be mapped stay in the original exceptions list with a warning; no amounts are invented. The warning count shows at the bottom when done (hover to view); full warnings are in result.json.
6. Emails are drafts only, never auto-approved or sent; an agent showing done means its function returned successfully, not that exceptions are handled or the books are closed.
7. Characters are static models. The web version's paper pick-up interaction wasn't ported to Godot and is out of scope for this round.
8. The model has 858 meshes: fine for a desktop demo, but not yet reduced or batched for mobile.

8. Editing the scene
scenes/main.tscn contains OfficeDemo, AgentState, AgentClient and AgentUI.
The office, camera and lights are created at runtime by scripts/office_scene.gd; the static editor viewport may not show the room, but it appears when running.
To inspect runtime nodes, switch the Scene panel to the Remote tab while running.
Swap the GLB: replace assets/office.glb and wait for Godot to reimport; the camera frames the model's bounding box automatically.
Direction: camera_direction in the OfficeDemo Inspector. Godot is Y-up; the front-angled default is (0.56, 0.72, 0.80).
Distance: camera_distance. With an orthographic camera, distance doesn't change size.
Size: camera_size_multiplier; larger values make the room smaller and leave space for the UI.
Lighting: light_energy of WarmWindowSun / SoftFrontFill and ambient_light_energy in office_scene.gd.
The Compatibility renderer is used so it runs locally; soft shadows are a real-time approximation, not Cycles area lights.
